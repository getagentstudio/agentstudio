## Verified adaptation findings

### Native File collection and membership

- `BridgeFileCollectionSource+Membership.swift:11–58` changes the member/layout set, increments `membershipRevision`, then awaits row removals, nested-member ownership changes, source opens and loose-document emissions before publishing `file.memberGroups`. This currently spans suspension points; PR2 must route the inventory, opened-document map, revision, and affected row puts/evictions through one N10 update and one sealed W4 batch (PD 173, 193–196).
- `BridgeFileCollectionSource+MemberForwarding.swift:64–75,178–195,222–254` accepts the outer collection source, forwards member output, suppresses child `sourceAccepted`/`memberGroups`, and translates member row/descriptor events. The integration keeps this behavior but routes its materialized output through N10’s one index/minter and W4’s keyed records (PD 173–175).
- `BridgeFileCollectionSource+MemberForwarding.swift:118–135` emits one collection-wide `finalWindow`/row count. PD requires per-member coverage; after a member failure, this final window must not be represented as a whole-scope snapshot that prunes that member’s last good rows (PD 195). Each member’s completion/status must remain local (PD 174, 193–196).
- `BridgeFileCollectionSource+MemberForwarding.swift:257–273` exposes one branch-summary slot from the first member. The combined PD says the first-member summary is not U12 change-set authority and places per-member change filters in PR3 (PD 197, 569–570). Keep the summary limitation in PR2; do not prematurely implement PR3 filtering here.

### Activation, receipts and reveal

- The outer handler captures generation before calling the presentation, but only checks it after the awaited activation returns (`Sources/AgentStudio/App/Coordination/BridgeNavigationCommandHandler+Activation.swift:58–60`). The pane then awaits the membership-update tail and source lookups before acquiring product admission/retaining a target (`Sources/AgentStudio/Features/Bridge/Runtime/BridgePaneController+FileActivation.swift:40–60`). This is the PD’s called-out order defect (PD 180): capture navigation generation before discovery and check it before every effect and receipt. The current handler captures before awaiting presentation but checks only after the return at lines 58–60, while the pane acquires product admission after its membership/source awaits at lines 43–52. PR2 should make the receiver-generation check govern those intermediate effects, and add the bounded session-replacement reissue behavior (PD 179–183).
- The current native receipt path validates admission and resolves `(displayPath, sourceId, subscriptionGeneration)`, then matches `commandId`; a commandless receipt supersedes a waiting activation (`BridgePaneController+FileActivation.swift:101–137`). Preserve that human-supersedes rule, but correlate the PR1 INST receipt by session/source, selection generation, command and descriptor (PD 183, 189).
- Page receipt construction still requires an active viewer and keys native correlation by matching `fileId` (`BridgeWeb/src/file-viewer/use-bridge-file-viewer-selection-receipts.ts:100–121`). Programmatic selection only selects a currently listed tree row and declares absence after the full unfiltered tree completes (`use-bridge-file-viewer-programmatic-selection.ts:85–126`); direct IPC reveal rejects a missing row immediately (`use-bridge-file-viewer-control-event-listeners.ts:119–125`). Adapt to PR1 INST and the PD point-lookup/pin/coverage protocol (PD 189–191). Keep `path_not_found` as the race outcome only where no complete coverage/lookup exists; this inventory does not propose retry behavior.
- Collection search uses the search operation’s own complete source coverage, not the displayed filtered/browsed tree (PD 213). Carry the command/result path through W1/N2 and query member sources through N10.

### Paint versus non-render state

The rAF queue that delays visible File rows is exact and page-side: `BridgeWeb/src/file-viewer/bridge-file-viewer-pierre-tree-runtime.ts:296–309` schedules the first row-patch drain at line 308 and schedules each subsequent entry at line 305. It advances the applied row-patch cursor only after applying that render entry. `BridgeWeb/src/core/comm-worker/bridge-main-file-display-patch-applier.ts:264–274` updates the logical File index synchronously and separately appends the Pierre display operations at 265–270. `bridge-file-viewer-app.tsx:460–483` is a different rAF: it records telemetry after `openFileState.status === 'ready'`; selection/content dispatch occurs synchronously at `bridge-file-viewer-render-snapshot-controller.ts:154–173` and selection commit at `bridge-file-viewer-app.tsx:258–276`.

The minimum “non-render state never waits on paint” boundary is therefore: keep `bridge-file-viewer-pierre-tree-runtime.ts:296–309` as presentation-only; ensure the PR1 batch receiver installs logical records/index before posting paint work (`bridge-main-file-display-patch-applier.ts:264–274`); route selection/content request from canonical logical identity rather than waiting for a rendered row (`use-bridge-file-viewer-programmatic-selection.ts:85–126`, IPC control listener `:119–125`); and emit INST from model/content installation, not the Pierre drain or telemetry callback (`use-bridge-file-viewer-selection-receipts.ts:100–121`, native consumer `BridgePaneController+FileActivation.swift:101–137`). No current source evidence shows selection/content open or control reply waiting on the rAF drain; the confirmed rAF wait is row painting. This is a carry-forward constraint, not a diagnosed product fix.
