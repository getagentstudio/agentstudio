# iOS Gateway hosting: evidence and qualification gap

The direct owner correction S28 requires a Rust Gateway on both macOS and iOS, talking to a UX client. This supersedes the earlier Mac-only Gateway boundary. It does not select an always-running mobile process or a Rust/Swift business API binding.

Apple's [background-execution guidance](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time) was read in full from its advertised [Markdown representation](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time.md) on2026-10-18. It explains that ordinary applications may be suspended after background transition and that extensions of execution are limited and must end. This supports an explicit mobile availability profile, not an unlimited networking-daemon claim. Specific background facilities and platform entitlements were not investigated or selected here.

The candidate iOS realization hosts the Gateway engine under the application lifecycle; its UX/socket contract remains distinct from whatever starts the Rust runtime. Concrete startup, Tokio runtime ownership, local socket custody, suspension/reconnect, safe binding/dependency compliance under IP6 and actual iOS build/device behavior remain qualification work. No compiled iOS Gateway, mobile socket interaction, FFI generation, simulator or physical-device experiment was run by this source review. A Mac build or codec self-roundtrip would not establish those boundaries.

## A safe startup candidate exists

Released `objc2-ui-kit` `0.3.2`, at upstream commit `7b1abfd750a2cacaea71d6a56ecfb83cb7de560b`, exposes a **safe** public `UIApplication::main` call accepting optional principal/delegate class names and a `MainThreadMarker`, returning `!`. Its raw argument access and UIKit call occur inside the upstream dependency. The wrapper requires the `UIApplication` and `UIResponder` features. [Released implementation](https://github.com/madsmtm/objc2/blob/7b1abfd750a2cacaea71d6a56ecfb83cb7de560b/framework-crates/objc2-ui-kit/src/application.rs#L87-L114) · [module gate](https://github.com/madsmtm/objc2/blob/7b1abfd750a2cacaea71d6a56ecfb83cb7de560b/framework-crates/objc2-ui-kit/src/lib.rs#L20-L21).

This supplies a source-supported candidate for Rust-owned application entry without a first-party Rust export or binding macro. A correctly linked, Objective-C-visible Swift delegate could be selected by its real class name, consistent with [UIKit's named-delegate contract](https://developer.apple.com/documentation/uikit/uiapplicationmain(_:_:_:_:)-1yub7). That mixed-language linkage is an inference from the APIs, not a built app. The wrapper's documentation example defines a Rust delegate using unsafe declarations; that example is not itself compliant first-party scaffolding and is not the proposed implementation.

This finding narrows the problem; it does not select a library or bootstrap architecture. The complete resolved dependency graph, safe argument construction under that graph, the real Swift delegate/scene setup, Tokio ownership, signing and physical-device behavior remain unqualified. The earlier Darwin `no_mangle` probe establishes its own rejected export forms only; it cannot prove every possible iOS startup route impossible.

## Safe callbacks do not establish the complete lifecycle

The inspected `winit` `0.31.0-beta.3` source provides safe active/inactive callbacks and calls the safe UIKit entry wrapper. Its foreground/background conversion, however, filters windows to its own `WinitUIWindow` class. It therefore does not establish those events for arbitrary Swift-owned windows. [UIKit event-loop source](https://github.com/rust-windowing/winit/blob/758a50e35a928dbf72bf05ae91f12fee7a540a83/winit-uikit/src/event_loop.rs#L168-L230) · [window filtering](https://github.com/rust-windowing/winit/blob/758a50e35a928dbf72bf05ae91f12fee7a540a83/winit-uikit/src/app_state.rs#L360-L373).

Active/inactive, foreground/background and individual scene state must remain distinct. A termination callback is not guaranteed for a suspended process that is killed. Qualification must observe the actual app/scene and socket state rather than assume a generic event-loop callback provides every lifecycle transition. This is source evidence only; no lifecycle experiment has run and no windowing framework has been adopted.
