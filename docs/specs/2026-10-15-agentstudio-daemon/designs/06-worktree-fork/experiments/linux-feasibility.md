# First Linux feasibility probe

This probe asks whether safe Rust filesystem primitives can supply the first building blocks of the Linux fork counterpart on one recorded Linux profile. It tests strict file cloning, constrained lookup, metadata and owned cleanup. It does not implement AgentStudio or establish complete worktree-fork parity.

**Current status:** procedure revised against Advisor challenge and primary sources; no probe executable, VM, fixture, build or experiment has been created or run. The owner has authorized Fly for Linux testing and requested login; Fly CLI login succeeded. Product source, configuration and vendors remain read-only. The primary [experiment map](../../../experiments/primary-experiments.md#e4--safe-linux-capability-and-parity) and [current requirements](../../../user-requirements.md) govern scope. The procedure still needs an actual pinned executable/image and environment qualification before a run can establish results.

## Question and deciding evidence

**Hypothesis:** on a supporting filesystem, a first-party safe Rust caller can request actual file-data cloning, preserve independent writes, constrain path resolution to the admitted root descriptors and realize explicitly measured inode metadata without silently copying bytes or discarding unsupported attributes.

The result makes a Linux backend candidate eligible for the later full fork experiments. A positive leaf result cannot close Git administration/index relocation, branch CAS, multi-file consistency, watcher parity or crash recovery. Existing Mac behavior is the reference to understand; Linux filesystem eligibility and normalization policy are still product decisions.

| Question | Supports under this profile | Falsifies or exposes a gap |
| --- | --- | --- |
| Strict clone | Safe wrapper's actual FICLONE call succeeds on verified regular-file descriptors; exact bytes match and subsequent writes remain independent | Silent byte-copy fallback, wrong file identities, source aliasing or incorrect content |
| Constrained lookup | Required safe API compiles for the exact backend/target; forbidden resolution fails and foreign fixture objects remain unchanged | Symlink/absolute/parent escape follows a foreign object, or implementation relies on a weaker flag than the claim |
| Metadata and custody | Each admitted attribute has a safe realization/readback path, and completed/failed/unsupported outcomes remain distinct | Silent attribute loss, privileged-only success passed off as ordinary-user behavior, foreign cleanup or work left running after reported settlement |

An absent kernel feature, denied mount privilege, missing safe wrapper or inadequate observer is **inconclusive for that arm**, with the precise gap. A validated unsupported-filesystem refusal is useful negative evidence, not a positive capability result or a Linux-wide verdict.

## One bounded environment

Use a newly identified experiment-only Fly app and one Machine. Select an image by immutable digest. Do not use implicit `--shell` app discovery: the installed CLI can reuse an existing interactive-shell app and retains it. Use an empty scratch working directory/configuration outside product source so the repository cannot contribute services, mounts, secrets or build context.

The initial envelope is one shared-CPU Machine, at most two CPUs and 2 GiB RAM, at most 8 GiB root storage, no public services/ports/IP allocation requested, no Fly volume and no remote builder. These are experiment limits, not a production sizing recommendation or a price quote. Capture the effective configuration; do not infer it from CLI defaults. A capacity refusal is an environment result, not permission to increase resources automatically.

Set process-exit restart to `no`; explicitly control any applicable autostart/autostop behavior and require no deliberate restart/suspend during a case. Unexpected lifecycle changes invalidate the affected case. Ordinary rootfs persistence is unnecessary: preserve receipts before retirement. Proxy lifecycle flags and process restart are different mechanisms.

The Machine needs an explicit, image-qualified **finite PID1 with a non-renewing 60-minute lifetime**, starting when that process begins. Record the init command/timebase and lifecycle receipt; verify restart `no` and automatic Machine removal on PID1 exit. Do not inherit an interactive shell image's default command or use an infinite keepalive. The timer is independent of the controller and performs no fixture work. Build/probe operations stay foreground; completion does not itself terminate PID1. Expiry ends unfinished work as inconclusive, and unexported receipts may be lost. Do not extend the lifetime to turn an incomplete run green. Qualify actual timer/VM-exit behavior; source configuration is not a measured billing bound during platform failure or a full cleanup receipt. Product session lifetime remains governed by U14/U15.

Root may prepare fixture users and, if available, small loop-backed filesystems inside this disposable guest. Run the effect cases as an unprivileged fixture UID without DAC/owner/mount capabilities. Use a separate read-only observer invocation with sufficient recorded privileges to inspect metadata hidden from that actor. Root without the necessary capability/LSM access is not a complete observer. These are test identities, not a selected production Host UID. Privileged observation/setup never counts as ordinary-user effect success.

No real checkout, credential, SSH agent, provider configuration or terminal content enters the guest. Cases use synthetic files only. No external Git remote, public listener, module installation or provider-host/kernel configuration change is needed by this first probe.

Use Fly's noninteractive HTTPS Machine launch/file-injection path and foreground `flyctl machine exec --json` as the **candidate operator path**. This controls fixtures; it does not change the required product client → Gateway → Host route. Avoid SSH/SFTP/`--shell` for this probe. Their agent/WireGuard behavior is mode-dependent and has extra resource/credential custody; it is not universally one detached-peer path.

Controller commands use a freshly owned private temporary state directory through supported `FLY_CONFIG_DIR`, rather than the owner's existing agent/cache state. Explicitly scope `FLY_AGENT_SOCKET_PATH` to an owned path there as well: an inherited socket override otherwise takes precedence, including for login/logout agent-stop attempts. Authentication in that isolated state is a prerequisite through the already authorized Fly login mechanism; current default-state login does not prove isolated-state authentication. No credential configuration is copied and no separate long-lived token is requested as a setup shortcut. Common flyctl preparers still write state; isolation is not a claim of zero local effects. Source inspection found a legacy PID preparer that can kill its recorded process, which is why the selected state must be independently owned. Actual local processes/state and resource receipts remain part of qualification.

Whether a live browser approval requires the owner is an observed flow condition, not something source or assumed AFK status can decide. If an actual approval/code is required, hold only dependent authentication/execution. Track login issuance, pending state, saved state and success separately: a failure after persistence can leave a credential. Retirement targets only this newly owned login. Normal saved-token logout at the inspected pin checks API acceptance before local clearing. Forced local clearing does not prove server revocation, and saved-token logout does not retire an overriding flag/environment credential. Record correlated server acceptance, local/pending-state residue and any scoped agent-stop outcome. Never log out or delete the owner's default state. [Authentication evidence](../../../research/evidence/2026-10-15-daemon-extraction-survey/e4-fly-authentication-evidence.md).

The build location is the disposable Linux guest. Select an immutable toolchain image containing the exact compiler/Cargo/native linker. Qualify its actual contents rather than assume every formatter/observer is present. For missing tools, use one declared in-guest package-preparation phase before freezing the environment: repository snapshot/metadata, package versions, archive hashes, signature verification, dependencies, installed tool versions and resulting services/processes are recorded. Candidate needs include loop/mount utilities, XFS/Btrfs formatters and independent ACL/xattr observers; exact packages follow actual command/provider inspection. If signed/pinned preparation or an independent observer cannot be qualified, those arms remain unavailable. Do not silently substitute the writer as its own semantic observer or disable package verification.

Local work only prepares reviewable source/lockfile/control files; it does not compile AgentStudio, cross-build on Sunbook or invoke a local/remote image builder. `--file-local` is a source-backed config-injection candidate for bounded text inputs, not an assumed large-binary channel. Record exact source bytes, aggregate/base64 request size, guest mode/hash/readback and actual accepted limits before compiling. No guessed API size bound is treated as fact.

Use an existing unchanged Cargo.lock and verify dependency archive checksums and first-party source hashes. A separately completed locked fetch may access the declared registries; the subsequent build/lint phase uses frozen dependencies. This permits explicit provenance without claiming that a lockfile is a sandbox or that network retrieval is inherently unpinned. The guest's permitted build network phase is distinct from the synthetic offline filesystem cases.

**Uncertain-execution rule:** if a result is lost, times out, is replay-rejected or lacks sufficient process-custody evidence, that invocation remains permanently inconclusive for this run. No later case, new invocation identity or changed source runs on that guest. End the run and retire the independently owned fixture/Machine with its resource evidence; a bounded read-only diagnostic may preserve observations but cannot upgrade the uncertain result to success. This deliberately pays for lost experiment work instead of adding a recovery ledger or assuming an orphan stopped. A failed retirement remains retained/unknown, never a completed cleanup claim.

Inputs are immutable within a run. Any source, lockfile, tool or config-injection revision starts a new experiment/lifecycle epoch and requires fresh environment/control qualification; use a fresh fixture rather than assume an update preserves or changes boot identity in a particular way. A prior uncertain guest is not reused. This is fixture sequencing, not product upgrade policy.

Boot ID alone cannot detect suspend; paired clocks are supporting observations, not guaranteed VM-snapshot/pause detection. Birthtime/generation fields are separately qualified evidence, not a universal uniqueness fix. Do not treat inaccessible state as absence. Guest observations establish this guest; they do not reveal or authorize changes to the provider's physical host.

## Filesystem selection algorithm

1. Inventory the guest before creating a corpus. Inspect the exact rootfs path as profile **P0**; its type and layering are observations. If it is overlayfs, record the applicable xino/copy-up configuration and calibrate opened-versus-reopened identity per profile. A non-directory object's reported device/inode can change under documented overlay configurations. If a verified image-owned lower-layer seed cannot be supplied, mark copy-up characterization unavailable; do not infer P0 identity stability from upper-only fixtures or transfer P1 results to it.
2. If P0 supports strict clone, it can supply the positive arm. Otherwise attempt one isolated scratch profile **P1** only when the guest already supports its driver, setup privilege and formatter: prefer a fresh XFS filesystem with reflink enabled; otherwise use Btrfs. Record the format invocation/features and mounted device. No kernel-module installation or hidden raw-volume fallback.
3. Bound scratch images to two files of at most 512 MiB each, and live synthetic logical payload to 64 MiB per case. Verify the selected formatter's minimum size and required features before formatting; do not deliberately choose an undersized positive profile. A setup-size refusal means that configuration is inadequate; do not raise the bound during the run or turn it into a Linux capability failure. A subsequent revised probe may choose an adequate documented size.
4. For an unsupported-filesystem arm, use a separately qualified mount **P2** whose real clone call refuses under valid descriptor/permission preconditions. Do not assume tmpfs or any named filesystem is unsupported forever.
5. For the cross-mount arm **P3**, verify distinct mounted-filesystem identities for the two descriptors. Rootfs versus scratch names alone are insufficient. A second Fly volume is unnecessary.
6. If the VM cannot supply a positive arm, keep its qualified refusal evidence and report the missing positive profile. Do not substitute byte copying or claim all Linux profiles failed. Raw Fly volumes and other Linux environments are later environment choices, not this probe's automatic escalation.

A loop-backed filesystem tests guest driver/API behavior on that setup. It is not proof about a direct production disk, a Fly volume, every filesystem or performance under the owner's workload.

## Exact fixture corpus and case sequence

All paths are below one newly created fixture envelope. `source`, `destination` and `foreign` are separate fixture roots; only the first two are admitted to the candidate operation. “Foreign” never means outside the disposable fixture. Give every object recorded custody/history evidence before a mutation or cleanup claim.

The corpus contains: an empty regular file; a 4 MiB regular file of 4 KiB blocks, each filled with `block_index mod 251`; a sparse 16 MiB file with distinct 4 KiB first/last blocks; one nested directory; one relative symlink; two source names sharing an inode; one FIFO; and fixed xattr/mode/time/ACL variants. Put `user.*` attributes only on regular files/directories; Linux excludes them on the symlink/FIFO variants. Privileged namespace fixtures require a successful setup receipt and a qualified observer. No device node or dataless/cloud-provider content is materialized.

Use separate fresh files per case. First capture metadata before byte verification can change atime. Set requested fixture timestamps, then record the actual realized values/precision; evaluate copies against that captured baseline. Linux-specific symlink modes/flags and unavailable ACL/xattr domains are explicit observations, not silently accepted product normalizations.

| Case | Action | Independent oracle |
| --- | --- | --- |
| C0 — observer calibration | On every profile, deliberately corrupt a copied fixture byte and write through a hardlinked alias. Compare retained-FD/reopened identity. Separately close all references, remove an object and create a fixed corpus of 64 labelled replacement objects; characterize any observed number reuse. Where qualified, exercise overlay copy-up | Content/alias observers detect the injected changes. Controlled creation receipts/content labels distinguish object history independently of a reused number. No observed reuse does not establish non-reuse; unavailable copy-up is explicit. These controls prove neither physical sharing nor universal persistent identity. |

A byte-correct copy alone cannot pass the clone-call requirement. |
| C2 — independent writes | After successful clone, alter one destination block and a different source block, checking both files after each operation | Each file changes only at its own write; no source hardlink alias. FICLONE's kernel contract establishes clone semantics; these checks do not independently measure saved physical blocks. |
| C3 — truthful refusal | Attempt clone on P2 and across P3, then separately use invalid descriptor rights and denied path permissions | Capture syscall, errno and all preconditions. Unsupported capability, cross-mount, bad FD and permission denial remain distinct; never map every errno to unsupported. Precreated owned destination files and any residue are accounted for. |
| C4 — constrained lookup | Resolve an ordinary child, `..` escape, absolute path, symlink ancestor and magic-link path with `BENEATH | NO_SYMLINKS | NO_MAGICLINKS`. | C5 — source replacement | Pause between planning and opening; replace the leaf/kind under controlled mutation. A matcher must not certify a foreign replacement from stale numeric identity alone. One-file atomic clone does not establish a coherent multi-file tree snapshot. |
| C6 — post-open parent move | Pause after opening a directory; rename it into the `foreign` root outside both admitted operation roots, on the verified same mount, and replace its old name before continuing | First prove rename succeeded; `EXDEV` is inadequate setup. Observe retained-FD writes in the moved directory and distinguish the foreign replacement at the old name. | C7 — raw clone metadata | Compare captured source and immediately cloned destination mode/UID/GID/times/xattrs/ACL/flags before explicit copying, through both actor and qualified read-only observer | Record properties supplied/missing and observer visibility separately. | C9 — link topology and node metadata | Build destination aliases from the cloned primary; use no-follow link stat/read/time/owner calls. Link text, node kind and foreign sentinel remain correct. No following chmod on a symlink target, blocking FIFO rendezvous or unsupported namespace is disguised as metadata success. |
| C10 — joined failure/cleanup | Trigger cancellation/failure at controlled leaf barriers. Use typed owner barriers and joined operations, not correctness sleeps, polling, repeated stress until green or wall-clock assertions. A runner-owned hang bound may terminate a stuck probe; its result is incomplete/inconclusive with the awaited fact named, never a semantic pass.

### C8/C9 metadata arms

Linux ACLs have a concrete safe candidate: read/write `system.posix_acl_access` and directory `system.posix_acl_default` through Rustix's `fgetxattr`/`fsetxattr`. The kernel routes these names through ACL parsing, ID/entry validation, ownership/LSM and filesystem checks. Absence of a convenience ACL-copy function is not proof that safe realization is unavailable. Use a nontrivial named-user access ACL and a directory default ACL, with all numeric IDs/mount mappings recorded. Include a malformed-format arm only after a valid control succeeds.

Read final ACL entries, numeric qualifiers, effective mask and mode through a separately qualified observer. Exercise actual access by a named fixture user granted read but not write, and by an unrelated fixture user granted neither; root cannot perform these effect checks. Characterize directory-default inheritance on a newly created child. Compare ACL-then-chmod with chmod-then-ACL on separate fresh fixtures and observe final semantics: chmod can change the ACL mask, ACL assignment can change mode, and an ACL equivalent to mode may disappear as an xattr. Neither setter success nor byte equality alone establishes intended rights. Darwin-to-Linux ACL mapping remains outside this Linux-only candidate.

Named Rustix `1.1.5` candidates for symlinks are `statat`, `utimensat` and `chownat` with `AtFlags::SYMLINK_NOFOLLOW`, plus `readlinkat`/`symlinkat`. A held parent plus leaf name still has a replacement window. The pinned no-follow `chmodat` route rejects symlink-mode changes; following the link instead would change the target and cannot substitute. For FIFOs, `mkfifoat` creates without rendezvous; `openat` with `RDONLY | NONBLOCK | NOFOLLOW | CLOEXEC`, followed by a kind check, is a candidate metadata FD when permissions allow it. `fstat`/`fchmod`/`fchown`/`futimens` operate on that held object. O_PATH is not a universal replacement for those setters. Node/attribute coverage and actual compilation remain per-profile qualifications. [Identity and metadata evidence](../../../research/evidence/2026-10-15-daemon-extraction-survey/e4-identity-metadata-evidence.md).

### Rust and clone proof boundary

The future probe is a small standalone fixture executable, not a new production crate/API. First-party code must forbid unsafe, retain owned descriptor custody and use the exact safe wrapper/backend it claims to test. One Tokio runtime owns asynchronous work; blocking filesystem work must leave the executor and be joined. Record formatting/lint/build outcomes separately from runtime cases.

For this probe's API qualification, the inspected Rustix candidate is `1.1.5`, VCS pin `287214b889865d8e1406a0ee71cc409b6f6191c8`; the earlier survey's `1.1.4` remains a separate historical source. The safe `ioctl_ficlone` takes destination first and source second. The public `openat2` export requires `linux_raw_dep`; the exact target/backend must demonstrate that cfg and compilation instead of silently falling back to weaker opens. Safe descriptor mode/owner/time/xattr APIs exist; C8 qualifies the composed ACL candidate rather than assuming a semantic wrapper is necessary. No safe FIEMAP wrapper was established in this crate. Unrun ACL/symlink metadata realization is not permission to omit it from full Linux fork parity. Details and primary anchors are in the [safe-primitives evidence](../../../research/evidence/2026-10-15-daemon-extraction-survey/e4-safe-linux-primitives-evidence.md).

This is a probe candidate, not a product dependency selection. Source existence is not compilation proof. Dependency unsafe scope remains the existing owner policy question; no waiver or claim that the entire dependency graph contains no unsafe is inferred.

Do not use `cp` success, sparse allocation, `du`, `st_blocks`, elapsed time or source/destination byte equality as physical-CoW proof. If FIEMAP/shared-extent evidence is available through an independently qualified observer, report it as supplemental evidence with its limits. Otherwise report kernel-accepted cloning and independent writes, without inventing a measured storage-saving result.

## Run result and next decision

Capability arms return **supported under the recorded profile**, **truthfully refused under observed preconditions**, **falsified**, or **inconclusive**, with primary observations. Characterization arms—identity reuse/copy-up, bind traversal, post-open movement and post-check unlink—report the observed behavior/limit or inability to observe it. They cannot be counted as capability passes merely because they reveal an expected limitation. Keep per-attribute/per-profile results; a summary cannot hide a failed arm or unresolved required guarantee. No product supported-filesystem policy follows automatically.

Preserve the run/source/dependency/environment manifest, fixture hashes/identities, raw bounded case receipts, independent readbacks and cleanup/resource disposition before retiring the Machine. Export no tokens, account metadata or arbitrary user data. No performance comparison is made from this feasibility run, and the Fly route is not the owner's Tailscale topology.

Retirement is tracked for the whole fixture lifecycle; the finite PID1 bounds its intended guest compute lifetime rather than every retained object. At creation, retain exact ownership receipts for the new app and Machine; never treat a matching name prefix or a reused shell app as ownership. PID1 expiry requests automatic removal with restart `no` even if the controller is lost; an interrupted launch, exec error or lost response still needs later independent inspection of that exact Machine. After evidence export, retire only experiment-owned resources through the supported Fly path and verify their resulting state. Account for the new app, isolated credential/state and any actually created local process/peer separately; Machine auto-removal does not retire them. The intended Fly volume/snapshot/public-allocation and SSH-peer inventories are zero; an unexpected resource is retained/unknown until ownership and disposition are established. A stop receipt or an empty filtered list alone is not complete retirement proof. This design issues no destroy command and claims no observed cleanup.

After this discriminator, the later [F01–F13 matrix](../../../research/evidence/2026-10-15-daemon-extraction-survey/edge-cases.md#forkplatform-counterpart-cases) still governs full fork work: nested repositories/submodules/alternates, index adoption, ignored/LFS policy, branch locks/CAS, non-UTF-8 names, platform metadata policy, cancellation across workers and complete typed residue. A result that exposes a necessary boundary change returns to design; it does not authorize a fallback or weaker parity.
