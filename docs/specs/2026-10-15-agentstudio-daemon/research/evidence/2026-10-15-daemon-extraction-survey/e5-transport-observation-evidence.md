## Priority, coupling and small-control versus bulk

`SendStream::set_priority(&self, priority: i32) -> Result<(), ClosedStream>` controls **locally buffered outgoing data**, initially priority zero; higher numeric priority is scheduled before lower priority. A changed priority may take effect only after already-pending data is transmitted. Many priority levels can have a performance cost. `send_fairness` changes equal-priority scheduling; it does not override higher-priority precedence. **S, P4/P5.**

Direction matters: setting the local send-half priority does not set the peer's outgoing response/output priority or the receiver's application-queue priority. Input/control going one way and terminal/diff/file output coming back require distinct sender observations. This is a consequence of the API's local-send scope, not a chosen layout. **I.**

Streams share the connection's congestion controller, connection flow-control credit and local send window. Each also has its own peer-advertised stream credit. Pinned `StreamsState::write_limit` takes the minimum of remaining connection credit and send-window allowance. A separate stream is not a reserved bandwidth/latency channel. Slow consumption can retain receive storage/credit; shared CPU, application queues, link contention and connection pressure can still affect other traffic. **S/I, P5.**

Quinn's reliable streams have no cross-stream ordering guarantee. On one ordered stream, later framed small-control bytes can remain behind an earlier bulky RPC response; `set_priority` cannot prioritize individual messages within that same send stream. Conversely, splitting streams introduces an application ordering question when effects depend on each other. These are measurement/contract distinctions, not a selection of multiple streams or connections. **S/I, P4/P5/P6.**

Record direction and traffic/stream assignment, unchanged versus changed priority, concurrent small control/bulky RPC response/terminal/file work, write-admission delay, per-owner queue age and application completion. Connection-wide counters alone cannot attribute a delay to one stream or distinguish congestion from CPU/admission/flow-control blocking. No public dedicated per-stream blocked-reason/queue-age/CPU metric was established in these inspected APIs. **I/U.**

## Compression observations and unresolved contract

Router has actual `async-compression` usage, not a null: proxy manifest features `tokio`, `gzip`, `zlib`, `brotli`, `zstd`; its locked version is `0.4.50`. Production `claude_edge/content_encoding.rs` parses HTTP Content-Encoding and creates a reverse-order decoder chain for **inspection copies**. Streaming completion spawns an async decoder observer through `TaskTracker` over a bounded one-message input channel; buffered error evidence uses an explicit decoded-prefix limit/completeness flag. Encoder calls found by the targeted search were tests. This is not production outbound terminal/RPC compression or an E5 performance result. **S, P2.**

For this exact library, Tokio `poll_read` delegates into generic polling that synchronously calls `decoder.decode` and `decoder.finish`. Router's observer awaits those reads in its spawned async task. Therefore its decode CPU is performed during polling on the task's executing thread; an async interface or TaskTracker does not by itself offload CPU to a separate executor. Actual runtime scheduling/CPU cost was not measured; this does not classify every possible compressor implementation. **S/I, P2/P7.**
