## Findings that affect G9

1. **`machine exec` uses the HTTPS Machines API in the default inspected path; it does not call the SSH agent/WireGuard setup.** It returns a buffered result rather than a console stream. Its server duration, command/output bounds and timeout process-settlement semantics are not established by the opened source/docs.
2. **CLI success is not guest success.** Pinned `runMachineExec` prints a nonzero guest exit code but returns no error solely for that result. Its `--json` output comes from a response struct that can omit zero `exit_code` and loses the live API's `exit_signal` field. A foreground control qualification must inspect the real result shape and guest outcome.
3. **“No WireGuard setup” does not mean “no local flyctl state.”** Common/auth preparers run before `machine exec` or noninteractive launch, create/check config state, can write cache, and conditionally kill a legacy agent from a PID record. A supported `FLY_CONFIG_DIR` override isolates that preparer's config-directory destinations; it is not a credential source or a guarantee of no other local effects.
4. **G9's classic SSH side effects are real but conditional.** SSH console/SFTP/shell call the agent path. The pinned CLI also has isolated-agent and token-gateway modes, so “always detached” and “always persists a registered peer private key” are too broad. No mode was observed or selected here.
5. **A foreground in-guest build need not download its toolchain if the selected immutable image already contains it.** That qualifies G9(a)'s necessity claim. No concrete toolchain/tools image, dependency set, payload size, native linker or execution duration has been qualified; the build remains unproved.

## Exact exec mapping and completion limits

CLI usage is `exec [machine-id] <command>` with one or two positional arguments: the command is one string. The CLI forwards it without adding a shell, splitting it into argv, or attaching stdin. This does not establish how the server interprets deprecated `cmd`; do not assume local shell quoting/redirection semantics apply there.

Pinned request/response fields (U1/U2):

```go
type MachineExecRequest struct {
    Container string // json:"container,omitempty"
    Machine bool     // json:"machine,omitempty"
    Cmd string       // json:"cmd,omitempty"
    Stdin string     // json:"stdin,omitempty"
    Timeout int      // json:"timeout,omitempty"
}
type MachineExecResponse struct {
    ExitCode int32 // json:"exit_code,omitempty"
    StdOut string  // json:"stdout,omitempty"
    StdErr string  // json:"stderr,omitempty"
}
```

The CLI sets `Cmd`, `Container`, `Machine` and `Timeout`; it does not set `Stdin` or expose a stdin flag in this command. `--container` and `--no-container` are mutually exclusive. `--timeout` is an integer in seconds with no specified default, so the pinned CLI obtains zero and JSON `omitempty` omits it when unset/zero. Zero/omission is not evidence of unlimited guest execution. No local maximum/range check appears in this command.

`func (f *Client) Exec(ctx context.Context, appName, machineID string, in *fly.MachineExecRequest) (*fly.MachineExecResponse, error)` sends `POST https://api.machines.dev/v1/apps/{app}/machines/{machine}/exec` under the default API base. An environment API-base override exists; no current environment was inspected. The HTTP client JSON-decodes the response before the CLI renders it. No PTY, streaming reader, interactive stdin, running-operation ID or completion subscription is exposed by this path.

For text output the CLI prints `Exit code: N` on nonzero, then stdout and stderr, and returns nil when the API/render path otherwise succeeds. For `--json` it serializes the struct directly. A zero `ExitCode` can therefore disappear due to `omitempty`; runtime qualification must observe the actual expected representation rather than assume an explicit zero field. The pinned response has no `exit_signal`, so an API-provided signal field is not preserved by this typed decoding/rendering.

The live OpenAPI instead offers `command: string[]`, labels `cmd: string` deprecated, and includes response `exit_signal`. Its `stdin`/`timeout` fields have no stated numeric size/default/maximum or timeout kill/reap guarantee. Neither the opened spec nor CLI establishes maximum stdout/stderr/command length, truncation behavior, shell parsing, or settlement of children after timeout/disconnect. The numeric limit for the separate Machine-state wait endpoint is not an exec limit.

There is also **no exactly-once execution proof**: Flaps' outer helper retries only GET, but U2 `http.go` configures shared transport retries for temporary errors and 502/503. `WithoutHTTPRetries(ctx)` controls that second layer; the inspected exec path does not set it. This identifies possible automatic retry, not an observed duplicate execution or a chosen mitigation. The client constructor has no explicit overall `http.Client.Timeout`; absence is not a server lifetime guarantee.

The Lead's proposed foreground control qualification (successful command, deliberate nonzero/signal, bounded output/footer) can close actual mapping/completion observations before build. A timeout/lost reply remains incomplete until actual process custody is established; it is not permission to detach work, poll a file, retry an uncertain execution or raise a limit to call it done.

## Transfer and foreground build viability

`func FilesFromCommand(ctx context.Context) ([]*fly.File, error)` reads each `--file-local` source entirely with `os.ReadFile`, base64-encodes it and places it in `raw_value`; parseFiles requires an absolute guest path. A pinned `File` also has a `mode` field. The create/update config path merges these files and sends JSON through the API, not through SFTP. Transfer identity still needs expected source bytes/digest and guest readback; an accepted configuration is not by itself proof of the intended installed content.

No numeric per-file, aggregate config/request, file-count or output maximum was established. The CLI helper has no local size guard in the inspected function; base64 adds approximately one third before JSON/config overhead. The guide's warning prevents claiming that a large executable, source/vendor bundle or complete dependency cache will fit. The actual source and lockfile have not been authored, so their transfer size is also unknown.

A digest-pinned image may already contain the exact Rust compiler/Cargo, native linker and filesystem observer/formatter tools. This avoids a necessary toolchain download; it does not prove a particular image contains those tools or has the required target architecture. Image reference resolution is distinct from local Dockerfile build, but flyctl's reference resolver still probes local/remote strategies and metadata paths. A no-local-builder/no-agent claim must cover that path too; a direct Machines API image field is a separate source-supported interface, not selected here.

Cargo's documented `--locked` preserves an existing dependency resolution but still permits network access. `--frozen` requires dependencies already available and prevents Cargo network access; it does not create a missing cache. Expected archive checksums and separately hashed first-party/path-source bytes strengthen provenance. A lockfile or generated checksum metadata is not a security sandbox, compiler proof, toolchain pin or proof that arbitrary dependency build scripts cannot perform their own effects.

There is no source-only reason a native Linux foreground build is impossible, and no source-only proof it fits the Machines exec lifetime or this probe's CPU/RAM/storage bounds. Required real completions remain transfer/readback, compiler/lint exit, expected executable digest/target and foreground probe settlement. Cargo `--quiet` reduces Cargo messages; it is not a hard stdout/stderr byte cap. A chosen output envelope needs an explicit overflow/incomplete outcome and preserved guest exit semantics. No build duration, toolchain image, output budget, detached builder, polling loop or fallback was selected.
