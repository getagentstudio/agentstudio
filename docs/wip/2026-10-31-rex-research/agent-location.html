Know where the agent runs—and what each pane shows

We need three different answers: where the terminal client is, where the conversation executes, and which conversation that client currently displays. Rex gives us useful terminal addressing and inspection patterns. The supplied research adds the missing client-selection problem, particularly when several clients share a background or remote server.

This is the second research track. The first covers UI performance and dynamic panes/tabs. This page incorporates the supplied research-note summary without treating their proposals or version-specific claims as implemented behavior.

Checked: current primary Rex/OpenCode documentation, a pinned ccmux TUI plugin, AgentStudio's existing identity/binding foundations, and the local Codex transport help. The unchanged ccmux TUI-plugin test file was also run: 26 tests passed, 0 failed.

Unverified: continuous selected-conversation detection in the installed Claude/Codex clients. The native attach/switch, footer, status-line and reconnect experiments below have not been run. No product implementation or new schema is approved here.

The pane contains a viewer; execution may be elsewhere

Suppose two idle conversations exist on one backend. A native CLI can remain in the same terminal while the user changes what it displays. Its process, connection and working directory can stay the same. The decisive observation is a change in the client's selected conversation.

This is an illustrative topology, not a claim that every provider supports the same modes. The backend need not learn the pane ID if its client can report the selected conversation through a channel AgentStudio can attribute to that pane.

What Rex actually gives an agent

Rex's CLI documentation defines stable session, window, block and connected-client IDs. A Rex session groups terminal work; it is not a Claude session or Codex thread. Its agent integration supplies terminal context through environment variables and a startup hook.

A process identity needs host and process incarnation, not just a reusable PID. A conversation needs its provider/backend scope and exact native ID. Official Codex documentation distinguishes thread.id from the session-tree root in thread.sessionId; use the exact thread when that is what the pane displays.

Represent several viewers of one conversation separately. A background conversation can have no viewer. An overview or picker can leave a client running without a selected conversation. Latest activity, most recent transcript and shared CWD cannot stand in for those facts.

A real client-side example: ccmux and OpenCode 2

The current ccmux TUI plugin runs inside the terminal client. It reads ctx.ui.router.current() and writes a marker containing that process's PID and a session ID. Its daemon can then associate the client process with a tmux pane. This addresses the problem of a shared backend process living outside every pane.

The implementation polls by default every 500 ms, normalizes the selected session to its root, and allows one live owner per session marker. Those are concrete limits for our purpose: exact child-conversation selection and two simultaneous viewers need different treatment. The polling interval is an implementation choice, not an AgentStudio requirement.

Official OpenCode TUI plugin documentation exposes the current route and a client connected to the server, including a remote server. A server event API is a different source of information. Confirm the event/reactivity API in the target client version before choosing a reporting cadence.

Obtain the identity first; choose its transport second

A client-side plugin, supported query or complete identity displayed by the native UI can supply selection. A socket, marker file or terminal escape sequence can carry it. Adding a transport does not make the selection observable by itself.

This is a candidate delivery map, not an existing AgentStudio protocol. WezTerm's user-variable event is concrete prior art: it delivers the receiving pane alongside the variable name and value. AgentStudio still needs a supported Ghostty receiver and verified behavior through zmx, tmux, SSH and reconnect; a title callback does not prove arbitrary metadata already reaches Swift.

Would making the TUI a child of agent-sessions help?

Yes, for launch identity and supervision. A child can use the current terminal and retain its normal TUI. Its parent can retain the launch pane and backend, observe process lifetime, and correlate a provider result when one is exposed. The parent does not automatically receive a copy of stdout when the child writes directly to the inherited terminal.

A second PTY could intercept bytes, but adds forwarding, resize and job-control work. First investigate the terminal state AgentStudio already owns. Capturing bytes still cannot reveal an ID that the client never exposes. An inherited FD or private socket is useful only when a hook/client integration actively uses it; a separately running backend need not inherit that local channel.

Version correction: the supplied notes describe a foreground/attach Claude launcher. The Router main snapshot checked here, 1cf0ce5a, still adds --bg in its Claude launch target and waits for the launched process's status. Treat those as different source baselines until the intended launcher branch is identified. The child's exit and the background agent's lifetime are separate facts.

What our current source already provides

  • PaneIPCIdentityOwner constructs pane-specific terminal environment and authenticated local IPC context.
  • The lifecycle contract keeps durable pane and zmx terminal identities separate and preserves the stored terminal identity during restoration.
  • SessionsBindingRecord already represents pane/provider-conversation bindings with generations, origin and lifecycle fields; conversation records retain provider/native IDs.

These are foundations checked at AgentStudio 2fa1b73c5, not evidence that continuous remote/native-client selection discovery is implemented. Reuse the existing owners when designing improvements. Exact backend scope, multiple-viewer representation, invalidation and persistence changes remain design questions; this research does not silently redefine current bindings.
