Identity when agents leave the pane

Earlier proposal: this page preserves the launch/registration discussion and its pinned source snapshots. Initial launch or attachment evidence does not by itself establish continuous visible selection.

A conversation is the continuing thing. A process runs it. A pane shows it. An attachment says which pane is connected right now.

Claude can continue in the background with no pane attached. Opening that same conversation in another pane keeps the conversation’s name and changes the attachment.

Record explicit links between conversations, process instances and pane attachments. Correlate work by the provider’s native conversation ID; establish the current viewer through an explicit attach operation. Proposed, not implemented or owner approved.

Read one background example, then the exact registration handshake, then shared servers and remote agents. Current implementation is separate from the proposal.

One conversation, three moments

Illustrative names: C17 is a provider conversation; A and B are panes.

What you doConversationCurrent attachment

A late hook must not move the conversation back to pane A. It reports work about C17. The attachment lookup says where, if anywhere, to display it.

This assumes the provider reports the same native ID. If a background operation creates a different native ID, it is a different conversation. A tool or subagent belongs to its parent only when the provider supplies that relationship.

Which name answers which question?

“Session” is overloaded. Keep these meanings separate.

ThingQuestionIdentity and lifetime
ConversationWhich Claude session or Codex thread?Provider + stable provider namespace + native ID. Survives a process restart when the provider resumes the same conversation.
Process instanceWhich running program?Host + boot instance + PID + process start/incarnation. A restart is a new process instance, even if a PID is reused.
PaneWhich terminal surface?Application scope + PaneId. It does not become the conversation ID.
AttachmentWhich pane/client is connected now?New generation for each explicit attach/rebind. A transport failure makes the connection unconfirmed until reconciliation.
Launch contextWhere did this launch originate?A launch correlation ID and immutable origin pane. Historical context, not proof of the current viewer.

The provider namespace is the stable scope in which its native IDs are unique, such as the same provider data environment on a remote host. A PID, temporary socket, CWD or hostname alone is not that namespace. Its exact contract needs provider-specific verification.

AgentStudio already makes PaneId independent of ZmxSessionID. The latter names the persistent terminal backend, not a Claude/Codex conversation. Preserve both identities.

See the proposed relationships and cardinality

A conversation can have no pane, or several viewing attachments where supported. A shared server process can carry several conversations. Viewing does not itself grant permission to send input: controller ownership follows the provider’s contract.

The process relationship records actual execution evidence, not every tool subprocess. Historical attachments remain history after they stop being current.

How the proposed association is established

Start: register the launch before it detaches

The launcher records launch context L1, origin pane A and observed process instance. When the provider identifies C17, its adapter records L1 → C17. Establish attachment A1 only with evidence that this client selected that conversation.

A direct CLI needs a supported launch argument, startup report or other provider-supported handshake. Which mechanism works must be verified per provider. Environment inheritance supplies launch context only.

Detach: preserve the conversation, retire its viewer

Explicit detach retires A1. It does not delete C17 or imply that its process exited. Network loss instead makes the connection unconfirmed until reconciliation.

Existing close/kill commands keep their existing meaning. This proposal does not change them into detach operations.

Reattach: confirm the native ID and create a new attachment

Pane B’s adapter selects/resumes C17 and checks the provider’s returned ID. Sessions creates attachment A2. Old events still belong to C17; they cannot revive A1. A connection reset does not invent a new conversation.

Who remembers it? Proposed: the existing Sessions persistence boundary owns conversation associations, launch history and attachment generations. The provider owns native conversation identity; the OS owns process lifetime; WorkspaceStore owns panes. Adapters submit evidence through the existing authenticated admission boundary. A correlation ID is not authentication.

If every launch goes through agent-sessions

Yes: this gives us a place to record the association before parentage is lost. Background services can remain. The necessary change is a launch-and-attach handshake, not a global pane variable on the server.

Step 3: how the correlation actually works

The caller holds two facts in the same operation: “I am serving pane P42” and “the provider returned conversation C17.” It sends both to AgentStudio, which stores their relationship. No PID needs to turn into a conversation ID, and no conversation ID needs to encode a pane.

Router is optional. It can supply the provider endpoint or carry a native connection, but AgentStudio owns its pane associations. The provider does not need to know AgentStudio’s pane ID when its client can return the native conversation ID.

R9 is a request identifier, not the discovery mechanism. It lets a retry of the same registration return the same outcome. The actual join is the caller’s retained pane context plus the provider’s returned native ID. The examples are illustrative names, not literal UUIDs or an implemented command syntax.

Before the provider repliesAfter it repliesStored association
Request R9: pane P42, endpoint E, conversation unknownThe same request receives C17 from EB9: pane P42 is linked to conversation (E, C17), with its relation and evidence source

Two simultaneous launches from the same directory retain separate request contexts. Each result is registered by its own caller; neither chooses the newest entry in a shared inventory.

Worked example: two launches finish in the opposite order

Illustrative proposal, not a runtime capture. Both launches use endpoint E1 and the same CWD. Their retained caller contexts keep the joins independent of completion order.

The launcher for R10 registers its own result C29. The launcher for R9 registers its own result C17. No ordering inference or PID lookup is used.

  • Retrying registration R9 with the same payload returns its original association.
  • Reusing R9 with C29 is a conflicting request, not permission to replace C17.
  • Conversation C17 on a different provider namespace E2 is distinct from (E1, C17).
  • Later attaching C17 in pane P99 is a separate registration with a new attachment generation; it does not rewrite the R9 launch origin.

Three callers can use the same registration action

CallerWhere the pane comes fromWhere the conversation comes from

A successful registration means the association was stored. It does not mean a provider was launched, a turn was sent, or a terminal was attached.

Manual registration is a declared link. It does not connect the terminal to the agent or prove that the pane displays it. An automatic launcher can record “launched from P42”; an actual attach adapter can record “attached in P42” after success. Keep those relationships distinct in storage and reads.

A future command could expose this action, but the generic registration action is proposed. It is not an existing command to copy and run. A pane-scoped caller still cannot retarget arbitrary panes; an owner-directed registration needs authority for its explicit target.

How a later background report finds the association

The background process reports its conversation; AgentStudio resolves the pane relationship. It does not need to recover an old parent PID. The authenticated provider adapter supplies the endpoint scope, and the report supplies the native conversation ID.

For example, the lookup can return “launched from P42” and “currently attached in P99.” Those facts can both be true. If no pane is attached, it returns no current viewer. If two panes are attached, it can return two authorized attachments; it cannot invent a unique current pane.

The endpoint scope matters: (E1, C17) and (E2, C17) are not assumed to be the same conversation. A raw conversation ID does not establish the sender’s authority. A stale launch-pane environment value cannot override the current attachment record.

This is a proposed reporting path. Registering an association does not automatically change today’s pane-scoped hook admission. Supporting it needs an explicit authenticated conversation-report contract at the existing owner; do not weaken session.event or fabricate a SessionStart.

Backgrounding or reparenting does not change the stored native conversation reference. A new native conversation, including a fork, gets a new reference. Reattaching the same conversation creates a new attachment generation without rewriting its launch origin.

Missing results, duplicate registration and stale panes
  • No native ID yet: the launch is pending; no confirmed pane/conversation association is created.
  • Result lost after a possible launch: the outcome is unknown. Reconcile only with exact provider evidence; do not guess from CWD or automatically launch another agent.
  • Registration acknowledgement lost: retry the same registration request ID. Same request and same data returns the original association; conflicting data must not overwrite it.
  • Pane/attachment retired: a late report cannot revive a live attachment. Preserve historical provenance only under its explicit retention contract.
  • Event arrives before registration: it cannot establish the missing pane association. This proposal does not promise lossless early-event delivery; buffering/replay needs its own explicit contract.

What must change in the current code

AgentStudio’s existing session.event method accepts provider hooks from their matching authenticated pane and applies process-chain/main-election rules. It is not a general owner command for linking an arbitrary external conversation. The proposed registration action needs an explicit command/IPC contract at the existing Sessions owner; do not simulate it with a fake SessionStart or weaken current hook admission.

Claude source result: the configured-source route already captures launch stdout/stderr and exit/unknown outcomes, but does not decode a confirmed new conversation reference. The existing job inventory separately provides job handle → optional session UUID. Joining the exact launch receipt to that inventory remains the missing adapter step.

Codex visible thread: native start/resume/fork replies identify conversations, but the TUI can also fork side conversations and tracks a separate active thread. Registering the launched conversation is narrower than proving the currently displayed thread. A viewing adapter needs the actual selection signal, not every loaded or forked thread.

Background, shared server, nested and remote

Shell job control: the process instance and conversation stay the same when the job moves out of the foreground. Process-group membership changes.

Claude background mode: several processes or a different parent chain may carry the work. The adapter needs the native session ID and an explicit launch/attachment association. Original parentage is supporting evidence, not required identity.

If Claude supplies a different native ID, create a different conversation. Link a parent only with explicit provider evidence. The inspected Herdr source does not establish which environment survives your installed claude --bg path.

Fully detached and never registered: if no reliable association can be recovered from a provider API/report, show “conversation known, pane unknown” or “identity unknown.” Do not guess from CWD or an old pane environment value.

A single server PID can carry C17 and C29 simultaneously. That PID cannot distinguish their selecting clients.

Application-controlled connection: correlate each start/resume request with its response. Record the returned native ID against the requesting pane’s attachment generation. A hook carrying that ID can then resolve the stored association.

Independent CLI: its adapter needs a supported signal exposing which conversation that CLI selected. Stamping the daemon’s environment cannot reveal this. Until a provider hook/API exposes that signal, shared-server pane discovery stays unsupported.

If two panes view one conversation, retain both viewing attachments where the provider permits it. Input/turn ownership still follows the provider’s controller rules; a new viewer does not automatically steal control.

zmx → agent: retain the terminal-backend identity and the explicit conversation association. Reconnecting to the terminal does not mint a new conversation.

zmx → tmux → agent: an adapter must capture the inner multiplexer target if inner-pane precision is required. Several inner panes can share one outer pane. Without an explicit inner target, attribution stops at the outer pane.

Remote host: collect process instances and native IDs there. Carry the remote provider namespace and explicit attachment over the existing authenticated transport. A local SSH PID names the transport, not the remote agent.

Herdr remote mode already selects a host and named Herdr session. That remote server owns its panes and receives hooks locally. Ordinary SSH inside a pane is different; a local Unix socket does not automatically exist remotely.

Three questions for every incoming event

  1. Which conversation? Resolve the native ID in its provider namespace. Unknown or ambiguous evidence stays unbound.
  2. Which execution source? Match registered launch/source generation and observed process incarnation when available. Reused PIDs and old generations do not identify a new execution.
  3. Which current viewer? Read explicit attachment records. An origin pane is history; it cannot create a current attachment.

A valid report can belong to a known conversation with no pane attached. Retain that evidence without pretending a terminal is connected. Duplicate reports must be idempotent; reports from retired attachments cannot revive them.

What storage retains, and what restart must recheck

Proposed durable data: provider conversation references, immutable launch provenance, attachment history and supporting evidence. Preserve the provider namespace through a daemon restart; record its new process instance separately.

Revalidate live connections on reconnect. Stored “was attached” history does not prove “is connected.” Exact retention, provider namespace, migration and controller contracts remain unsettled.

Recommended direction and its cost

Recommendation from the 🦉 Advisor: durable conversation identity plus explicit client attachments, reusing the existing Sessions owner. This is a design recommendation, not an implementation or acceptance verdict.

ApproachGainCost and limitation
Launch environment + PID discoverySmallest change; useful for direct launches and known terminal jobsUsers lose reliable current-pane attribution after unsupported detach/shared-client transitions. Original context cannot reconstruct a missing viewer.
Dedicated provider runtime per paneOne runtime’s environment can name one paneUsers pay extra resources; maintainers verify provider launch behavior. Later reattachment and pre-existing agents remain unsolved by isolation alone.
Explicit conversation + attachment recordsRepresents background work with no pane, reconnects and shared runtimesMaintainers build adapters, durable association and generation handling. A provider without native-ID/client-selection evidence stays unsupported.

A dedicated runtime can be a deliberate provider fallback. It is not a substitute for naming the conversation. Do not promise arbitrary detached-process discovery.

Assumption to test first: the provider exposes its selected native conversation to the component controlling the pane. If it exposes only a daemon PID, this adapter cannot establish the attachment. Verify that boundary before committing to storage changes.

If deferred, the research remains usable; implementation of new attachment semantics and storage/provider contracts waits. Reading this proposal requires no changes to running agents or hooks.
